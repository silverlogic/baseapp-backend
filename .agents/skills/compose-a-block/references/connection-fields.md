# Connection Fields

Every list field is a Relay connection built with `baseapp_core.strawberry.connections.connection`.
It wraps `strawberry_django.connection`, so the optimizer always runs on it — there is no
unoptimized connection class to pick by mistake.

## Declaring one

```python
from baseapp_core.strawberry import CountedConnection, type_for_model
from baseapp_core.strawberry.connections import connection

UserLazyType = type_for_model(User)


@strawberry.type
class UsersQueries:
    @connection(CountedConnection[UserLazyType] | None, filterset_class=UsersFilter)
    def users(self, info: Info) -> Iterable[Model]:
        if info.context.user.has_perm(f"{User._meta.app_label}.view_all_users"):
            return User.objects.all()
        return User.objects.none()
```

A root connection with no resolver lists the type's model through its `get_queryset`:

```python
    all_pages = connection(CountedConnection[PageLazyType] | None, filterset_class=PageFilter)
```

`connection(...)` adds `first` / `last` / `before` / `after` / `offset` and one argument per
FilterSet filter. Options:

| Option | Effect |
|---|---|
| `filterset_class=` | FilterSet arguments, applied to the resolver's queryset |
| `filter_overrides={"name": Type}` | fix the inferred GraphQL type of one filter argument |
| `default_first=10` | `first: Int = 10` |
| `max_results=` | page-size cap |
| `prefetch_related=` / `annotate=` / `only=` | optimizer hints, as on any field (`optimizer-hooks.md`) |

Declared connections are nullable (`CountedConnection[T] | None`). Connections for model relations
are generated by `django_type(relations=...)` (non-null, filtered with the related type's
`filterset_class`) — never declare those by hand.

## `CountedConnection`

`baseapp_core/strawberry/connections.py`. Adds `totalCount` (computed with a window function in the
same query when selected) and `edgeCount` to strawberry-django's list connection; edges have a
nullable `node`. Always use it; it is the connection shape the schema exposes everywhere.

## Return the queryset, never a list

Resolvers must return an unevaluated queryset. The connection extension applies the FilterSet,
optimization *and* pagination; hand it a list and you lose all three, and slicing happens in
Python after loading every row. Never call `optimize()` on the returned queryset yourself.

Empty results are `Model.objects.none()` — no marker needed.

Order by a stable field. Cursor pagination needs deterministic ordering or pages duplicate and drop
rows.

## FilterSets

- A FilterSet that orders by an annotated alias adds the annotation itself in `filter_queryset`:
  the FilterSet runs after the optimizer (`baseapp_comments/strawberry/filters.py`,
  `annotate-queryset.md`).
- Relay-id filters use `GlobalIDFilter` / `GlobalIDMultipleChoiceFilter`
  (`baseapp_core/strawberry/filters.py`); they map to `ID`.
- A resolver that needs a filter value itself: leave `filterset_class` off, declare the arguments
  on the resolver and call `apply_filterset(...)` yourself.

## Nested and same-type connections

`comments -> comments`, `profile.members`, connections inside interfaces: each level is optimized
for its own selection by strawberry-django. Interface connections whose relation runs through
`DocumentId` need a `prefetch_related` hint (`optimizer-hooks.md`, Pattern B).

## Anti-patterns

- Returning a list, or calling `.all()` / `list()` to "materialize" before returning.
- Calling `optimize()` inside a resolver.
- Using `strawberry_django.connection` or `strawberry.relay.connection` directly — you lose
  `offset`, FilterSet arguments and `CountedConnection`'s shape.
- Declaring by hand a connection the relation generator already exposes — duplicate field, wrong
  nullability.
- A connection with no stable `order_by`.
